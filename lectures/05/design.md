# Day5 発展：質問に応じて候補を選ぶGraph

## 1. 解きたい質問

講義を振り返るとき、似た用語を同じ仕組みだと捉えず、離れたページの説明を合わせて理解したい。たとえばLoRAで学習する追加パラメータと、外部メモリから会話に戻す情報は異なる。検索結果が一方の話題に偏ると、正しい比較を説明する根拠が足りなくなる。

この用途に対し、単一ページ、複数ページ、講義横断、資料に答えがない質問の4種類を事前に用意した。問い・期待する説明・参照候補は[questions.json](questions.json)に固定する。参照候補は取得後の確認にだけ使い、検索器・生成モデルには渡さない。

## 2. 使うデータ

公式教材の確定コミット`1ce722c2816b70ef62891a6378b2478af555e3fd`を利用する。

| データ | 持ち方・役割 |
|---|---|
| `lectures.json` | 講義→章→ページのJSON。1ページが1チャンク。本文と引用情報の原本 |
| `index.sqlite3` | 同じページの本文・メタデータと768次元float32埋め込みを持つ`chunks`表 |
| `graph.json` | ページと用語のノード、`next_page`・`mentions`等の辺 |
| `tree.json` | 配布資料の階層の記録。今回の取得器ではTree探索を使わない |

対象は`lec01-main`73ページ、`lec02-main`70ページ、`lec03-main`71ページの合計214ページ。教材JSON全体の438ページには広げない。DBとJSONの全行・本文・引用情報を照合し、教材のSHA-256を保存する。ページの埋め込みを作り直さず、配布DBを読み取り専用で使う。

## 3. 基本RAG

1. 質問文を`gemini-embedding-001`、`RETRIEVAL_QUERY`、768次元で埋め込み、正規化する。
2. 全214ページとのコサイン距離を計算する。
3. 距離が小さい上位5ページを返す。同距離はページID順とする。

これは講座のベクトル検索と同じ順位基準である。追加の実行環境を不要にするため、SQLiteのベクトルを`struct`で読み、`math`で内積を計算する。`sqlite-vec`と浮動小数点の積和精度が異なるため、ほぼ同点の項目では微小な順位差があり得る。今回の2方式は同じ計算関数を使う。

## 4. 改良Graph

**変更するものは取得方法で、最終的に返すページ数は基本RAGと同じ5件にする。** 単純に多くの本文を渡した効果と、候補選択の効果を混ぜないためである。ただし5件の文字数は一致しないため、実際の入力トークン数を測る。

### 候補を広げる

- 基本RAGの上位3ページを入口とする。基本RAGの上位5ページは候補に残す。
- `next_page`は同じ資料の中だけで最大2 hopたどる。
- `page → term → page`も2 hopでたどる。ただし、質問に用語の別名が現れ、かつその用語が214ページ中32ページ以下に現れる場合だけ使う。
- `contains`と`related_term`は使わない。関係を増やした効果を今回の設計に加えない。
- Graphで加えるページは、質問のベクトル順位50位以内に制限する。全候補は最大24件とする。

別名はUnicode NFKCと大文字・小文字の正規化で照合する。英字には語の境界を設け、`QLoRA`の一部を`LoRA`と誤認しない。一般的な用語から広範囲へ拡散することを避け、質問に関係する少数の関係に絞る。

### 5件に選び直す

検索1位は残し、残りを次のスコアで順に選ぶ。

```text
0.72 × 質問とページのコサイン類似度
+ 0.23 × まだ取得していない質問用語のIDF重み付きカバー率
− 0.05 × 選択済みページとの最大コサイン類似度
```

意味的な近さを主にしつつ、別の質問用語を説明するページを拾い、似たページだけで枠を埋めにくくする狙いである。係数、hop、上限は実行前に決めた設計値であり、この4問の実測結果を見て調整した値ではない。最適値だとは主張しない。

取得した経路と選択スコアを記録する。経路が説明できても、本文が答えを支えるとは限らない。Graphの用語付与漏れ、入口の取り違え、順位50位の外にある根拠は残る失敗要因になる。

## 5. 比較で固定する条件

| 条件 | 設定 |
|---|---|
| 質問 | 事前定義した同じ4問 |
| 対象資料 | 第1〜3回本講義214ページ、同じ確定版 |
| 回答モデル | 既定`gemini-3.5-flash-lite`。実際のモデル名・返却モデル版を記録 |
| 生成設定 | temperature 0、出力上限4096トークン、同じ共通指示 |
| 最終取得件数 | いずれも5ページ |
| 生成処理 | 1回の取得の後、1回の生成API。会話履歴は引き継がない |
| 反復 | 既定2回。各質問で基本→Graph／Graph→基本を入れ替える |
| 質問埋め込み | 各試行で独立に取得。同じ文字列・モデル・次元。キャッシュしない |
| 実測時間 | 質問埋め込み・取得・生成を含む。教材準備・試行間待機は除く |

今回は**取得方法を切り分けるための制御したRAG比較**である。講座の`app.agent`が検索語・ツール呼び出し回数を自律的に決めるループを、そのまま測った結果ではない。どちらの方式も同じ生成器を使うので、得られた差はこの固定した実験の範囲で解釈する。

両方式に同じ質問を渡すが、埋め込みAPIをそれぞれ独立に呼ぶため、返却ベクトルのハッシュも残す。temperature 0も完全な再現性を保証しない。返却モデル版・試行順・反復ごとの回答を確認する。

## 6. 評価と費用

自動計算するのは、事前に選んだ参照グループのうち何組が取得されたか、抽出できた引用ページが取得本文に含まれるか、時間、使用量、推定費用である。

参照グループはグループ内のページがOR、グループ間がAND。同じページが2つの事実を支えれば複数グループを満たす。候補は網羅的な正解集合ではない。**取得率や、引用ページが存在する率を、意味的な正答率として扱わない。** 資料に答えがないq4の取得率は対象外とし、自動的な合格にしない。

人手確認では、回答の正しさ・引用の主張に対する裏付け・資料外の数値を作らず回答を保留したかを分ける。各試行の回答と本文を読み、理由を記録する。改善が出なければ「改善は確認できなかった」と書く。全問で失敗を観察しなければ架空の失敗例を作らず、未検証範囲・残る制約を書く。

料金はGoogle公式の2026年11月17日確認時点のStandard有料枠の単価で見積もる。既定モデルでは100万トークン当たり入力$0.30、確認できたキャッシュ入力$0.03、思考を含む出力$2.50。入力・出力・思考・キャッシュの実際の返却値を記録する。無料枠の適用や請求額そのものは判定しない。使用量または単価が確認できなければ`算定不可`とし、0円に置き換えない。質問埋め込み・索引構築費用は生成API推定費用から除く。

4問×2反復は小規模な用途別の比較であり、方式全体の性能差や統計的な優越性を示すものではない。精度・根拠・時間・費用の観察から、今回の講義復習用途への採否を決める。

## 7. 実行と提出の証跡

- `config.json`：質問・参照候補・実行順・モデル・コードのハッシュ・教材版。
- `records.jsonl`：成功・失敗を含む試行記録。取得本文・経路・回答・使用量・時間。
- `report.md`：比較表と回答。自動指標と人手判定を分ける。
- `reference_pages.json`：人手確認用の参照本文。生成には渡していない。
- `human_review.json`：回答・引用の確認と、実測に基づく考察。
- `source_snapshot/`：実行したコードと条件の写し。APIキーや教材DBは含めない。

部分失敗は未完了として保存し、自動再試行はしない。`--resume latest`を実行すると、同じコード・データ・条件の完了していない試行だけを再開する。失敗したAPIも課金される可能性があるため、成功した試行の費用合計を請求総額とは呼ばない。
